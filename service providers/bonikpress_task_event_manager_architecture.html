05 / RUNTIME

From definition
to occurrence.

A task is reusable. An execution is one particular occurrence of that task.

Task trajectory

01 · Define
Establish the task's identity and expected structure.
02 · Register
Make the task known to the provider.
03 · Configure + schedule
Set the schedule, configuration and required conditions.
04 · Become eligible
Schedule arrives and conditions are satisfied.
05 · Execute
Start a particular execution and delegate domain operations.
06 · Complete/fail
Lifecycle reaches a terminal state and diagnostics capture the trail.

Event trajectory

01 · Define
Establish a meaningful ecosystem event.
02 · Register
Make the event available as a known hook point.
03 · Register callbacks
Associate responses with the event.
04 · Occur
The event actually happens.
05 · Resolve + dispatch
Find relevant callbacks and dispatch the event.
06 · Invoke + diagnose
Callbacks run; outcomes and failures remain observable.

07 / BOUNDARY TEST

What this provider
must not become.

Feature richness is not architectural quality. Unnecessary authority creates coupling.

×

Not an HTTP manager

Tasks can require requests. Request construction, validation, dispatch and response handling remain with Request Manager.

×

Not a data manager

Tasks can operate on data. Retrieval, persistence, querying and integrity remain with Storage & Data.

×

Not a UI manager

UI actions can create or influence tasks. UI components and UI-originated actions remain with UI Provider.

×

Not Core

Task lifecycle must not become ecosystem/provider lifecycle. Core remains the ecosystem authority.

×

Not a universal workflow engine

Task/event relationships do not automatically justify a generic workflow abstraction.

×

Not a business-logic layer

Execution coordination is different from owning the actual domain operation performed by a task.

08 / ARCHITECTURAL AUDIT

Challenge before
implementation.

Every provisional sub-role must earn its place.

Determine whether these are truly separate concepts or whether they should converge into a simpler readiness model. Scheduling answers when to evaluate; conditions answer what must be true; eligibility answers whether execution can begin.
Registration defines what exists; resolution finds the event and its relationships; dispatch causes an occurrence to reach its registered responses. The final architecture should decide which distinctions are architectural and which are implementation details.
A task or event can be invalid, unavailable, disabled or simply not eligible. These states may be useful, but they should not become separate concepts without a clear semantic difference.
Initialization may simply be one phase of state management. The final state model should remain minimal and explicit.
These are legitimate lifecycle concepts but may not be needed in the first implementation. They should be introduced when the runtime requirements justify them.
These are deliberately not major roles in the current model. They are possible implementation mechanisms, not automatically core architectural responsibilities.
