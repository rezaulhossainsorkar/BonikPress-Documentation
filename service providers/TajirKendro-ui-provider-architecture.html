02 · Infrastructure

Clear boundaries make the provider powerful.

The UI Provider coordinates UI-originated action behavior while neighboring authorities keep their own domains.

It may start an action that eventually needs HTTP or data, but those concerns remain with Request Manager or Storage & Data.

Authority 01

↔

↔

UI Provider owns

The action because it began at the UI

Target identity, action invocation, lifecycle state, completion/failure and action-specific diagnostics.

UI Provider does not own

The downstream domain operation

HTTP is not UI infrastructure. Data is not UI infrastructure. Ecosystem lifecycle is not UI infrastructure.

Boundary principle

Coordinate, don't absorb

The provider may hand work across boundaries, but ownership stays with the authority designed for that concern.

03 · Runtime journey

From a reusable button to a real action

The flow is intentionally linear and easy to reason about: the component declares intent, the UI Provider governs the UI action, and downstream authorities handle their own domains.

The calling mechanism is predefined once. Consuming code selects a reusable component and identifies its target instead of rebuilding event handling, lookup, validation and diagnostics.

01

Interface component is rendered

A reusable TajirKendroPress component appears in the consuming plugin, bundle or ecosystem interface. Its visual and interaction behavior comes from the shared UI library. The consumer supplies specifications such as labels, appearance and the action target rather than rewriting the component's internal markup and event plumbing.

Reusable UI
02

User expresses an intention

The interaction produces a target identifier. The UI does not need to know which callback, request pathway or data operation eventually fulfills the intention. This separation is what allows the same component pattern to be reused in very different products without coupling the visual component to a particular business operation.

Target declared
03

Action target is resolved and validated

The provider determines whether the requested target exists, is properly registered, is usable and can accept the invocation. This is also the natural point for developer-facing validation: a missing callback, duplicate target or invalid specification can be detected before the action reaches an unpredictable downstream state.

Target Management
04

Action lifecycle begins

A concrete invocation is initialized and moves through controlled states. Execution coordination happens without stealing ownership from Request Manager or Storage & Data. The provider owns the UI-action journey, while the domain provider owns the domain work.

Lifecycle Management
05

Outcome is observed and explained

The action reaches completion, failure or another terminal state. Diagnostics preserve enough context to understand what happened and why. A useful outcome is therefore more than “callback returned”: it tells the ecosystem whether the intended action was accepted, executed, completed, failed or stopped.

Diagnostics
04 · Major roles

Three domains. One coherent action system.

Every responsibility should fit under one of these three roles. Their sub-roles provide structure without turning the provider into an ecosystem-wide service container.

ROLE 01

Action Target Management

Controls what UI components are allowed to invoke and how those targets are represented. A target is the stable identity of an intention, not the implementation detail of the callback behind it.

  • Target Definition
  • Target Registration
  • Target Identification
  • Target Resolution
  • Target Validation
  • Target Availability
  • Target Configuration

Its key question: “When a component says this target name, can the provider reliably identify the action that name represents?”

ROLE 02

Action Lifecycle Management

Controls the journey of a particular UI-invoked action from invocation to terminal state. It gives the action a predictable beginning, middle and conclusion rather than treating a callback as an isolated function call.

  • Action Invocation
  • Action Validation
  • Action Initialization
  • Action State Management
  • Execution Coordination
  • Completion Management
  • Failure Management
  • Cancellation & Cleanup

Its key question: “What state is this UI-originated action in, and what is the next valid transition?”

ROLE 03

Action Diagnostics

Makes UI-invoked action behavior visible, traceable and understandable for development and troubleshooting. The goal is not noise; the goal is enough context to explain an invocation when something goes wrong.

  • Action Observation
  • Action Logging
  • Error Diagnostics
  • State Diagnostics
  • Execution Tracing
  • Diagnostic Reporting

Its key question: “Can a developer understand what happened to this action without reconstructing the entire system manually?”

09 · Ecosystem usage

The same infrastructure can serve very different components.

The architecture becomes valuable when small plugins, large plugins, bundles and ecosystem-level products can all use the same action vocabulary.

↗

A small plugin

A developer wants a standard button that invokes “refresh_table”. They should not rebuild event binding, target lookup, lifecycle bookkeeping and diagnostics inside the plugin. The plugin consumes the shared component and declares its target.

“I provide the intention; the provider provides the common invocation machinery.”
◆

A large plugin or bundle

A more complex product can define many targets for different interface actions. Because target management is centralized, the bundle can keep its feature code focused on domain behavior rather than repeating UI plumbing for every screen.

“Many features can share one action model without sharing their business logic.”
◎

The wider ecosystem

As more TajirKendroPress components consume the provider, the action system becomes a common contract. Developers can recognize the pattern across products even when the targets and downstream operations are completely different.

“The ecosystem gains consistency without forcing every product into the same implementation.”
10 · Design contract

What should a consuming developer experience?

The best infrastructure is often visible through how little repetitive code it requires from the developer using it.

Rule 01 · Declare intent

A UI component should identify the action target it wants to invoke instead of embedding the implementation of that action.

Rule 02 · Reuse the mechanism

Click handling, target lookup, validation, lifecycle entry and diagnostics should be predefined infrastructure rather than copied into every component.

Rule 03 · Keep targets stable

Target names should represent meaningful intentions and remain independent from temporary implementation details such as a specific JavaScript function name.

Rule 04 · Fail clearly

If a developer requests a target that does not exist or cannot execute, the provider should produce a clear diagnostic instead of a mysterious silent failure.

Rule 05 · Preserve ownership

When execution crosses into HTTP, data or ecosystem infrastructure, the provider should coordinate the handoff rather than recreate those systems.

Rule 06 · Make state meaningful

Lifecycle states should communicate real action conditions and provide useful checkpoints for interfaces and diagnostics.

Rule 07 · Prefer predictable contracts

A smaller, explicit contract is more valuable than a clever universal mechanism that becomes difficult to understand or debug.

Rule 08 · Grow by pressure

New infrastructure should appear when real ecosystem requirements demand it, not because the provider could theoretically support another abstraction.

11 · Implementation philosophy

Start simple. Earn the complexity.

The provider can begin as a compact reusable library and progressively gain stronger action infrastructure as real use cases reveal the need.

Stage A — shared UI vocabulary

Establish component identifiers, rendering contracts and a consistent way to consume UI components. The first objective is reuse, not a giant framework.

The ecosystem should quickly gain a reliable way to say “render this known component with these specifications.”

Stage B — target vocabulary

Introduce named action targets and the registration mechanism behind them. At this point, the provider becomes more than a component library: it becomes a controlled bridge from interface intent to action execution.

Stage C — lifecycle contract

Add validation, initialization, state transitions, completion and failure handling. The objective is to make every action behave according to the same broad lifecycle model.

Stage D — diagnostics

Once the lifecycle exists, diagnostics have meaningful events to observe. Add tracing and reporting around actual developer needs instead of building an abstract monitoring system first.

Guiding principle: architecture should make the common case simple while keeping the uncommon case understandable. The provider should not require every consumer to understand its internals merely to render a button.
07 · Work trajectory

Build the concept before building the machinery.

Build in stages: shared UI vocabulary, target contracts, lifecycle machinery, then diagnostics and hardening. Complexity should be earned by real use cases.

08 · Architectural conclusion

A focused provider is easier to scale.

TajirKendroPress UI Provider should become the common language between reusable interfaces and UI-originated actions. Components stay simple. Targets stay identifiable. Lifecycles stay controlled. Diagnostics stay useful. Other providers keep ownership of their own domains.

In practical terms, this means a developer should be able to think in terms of “which reusable component do I need?” and “which action target should this component invoke?” rather than “how do I rebuild the entire interaction infrastructure for this screen?” The provider absorbs that repetition once, centrally and consistently.

At the same time, the architecture remains disciplined: Core owns ecosystem lifecycle, Request Manager owns HTTP and request concerns, Storage & Data owns data concerns, and UI Provider owns the interface and the lifecycle of actions that begin from that interface.
