01 · Ecosystem Lifecycle

Govern the life of Commerce.

Lifecycle is about controlled transitions: how the ecosystem starts, discovers itself, resolves relationships, becomes operational, and eventually shuts down.

01 · BootstrapStart the Core execution context.
02 · EnvironmentVerify WordPress, PHP, WooCommerce, and platform prerequisites.
03 · DiscoveryFind participating components and providers.
04 · RegistrationTurn discovered entities into known ecosystem components.
05 · ValidationCheck declarations and structural correctness.
06 · ResolutionResolve dependencies, compatibility, capabilities, and conflicts.
07 · LoadingMake resolved components available to the Commerce runtime.
08 · InitializationAllow participating components to prepare themselves.
09 · ReadyMark the ecosystem or component as ready for operation.
10 · RuntimeHand ongoing operational concerns to Runtime & Coordination while remaining part of the ecosystem lifecycle.
11 · ShutdownProvide a controlled termination point for the Commerce runtime.
Important distinction

Loading is retained as an ecosystem concept, but Core does not need to invent a replacement for WordPress's native plugin-loading mechanism. Initialization remains an explicit Commerce lifecycle concept.

04 · Provider Management

Five providers. One mandatory foundation.

Provider Management governs the infrastructure providers themselves. All five are mandatory Commerce infrastructure, even when an individual installation does not actively use every capability they expose.

01

Core Manager

The kernel that governs lifecycle, registry, relationships, runtime coordination, configuration, and extension infrastructure.

02

Data Manager

One gateway to platform data: retrieval, CRUD, queries, filtering, pagination, metadata, custom tables, caching, and normalization.

03

Request Manager

One request lifecycle for AJAX and REST, parsing, sanitization, security checks, validation, and standardized responses.

04

UI Manager

One reusable admin experience for tables, filters, search, pagination, forms, modals, notices, and components.

05

Task & Event Manager

Work later and react cleanly through queues, background jobs, scheduling, retries, and ecosystem events.

Manage the provider

Provider Boundary

Core coordinates providers. It does not become them.

Data Manager

Owns existing platform/application data and the unified data access layer.

Request Manager

Owns request processing, security, validation, and standardized request/response flow.

UI Manager

Owns reusable administrative presentation and interaction primitives.

Task & Event Manager

Owns queues, background work, scheduling, retries, and event-oriented processing.

Core

Knows provider state, dependencies, availability, and participation. It coordinates rather than absorbing their business.

Future Payments

Does not use this five-provider Commerce foundation. Payments will have its own future architecture.

06 · Runtime & Coordination

Know what is happening now.

Lifecycle describes where the ecosystem is in its controlled startup/shutdown journey. Runtime describes the ecosystem's current operational condition.

TWO DIMENSIONS

Runtime State

“What condition are we in?”

DEGRADED

RUNTIME STATE

Current condition

Tracks the operational state of Commerce and its participants.

READINESS

Ecosystem readiness

Determines whether Commerce as a whole can operate, distinct from individual provider readiness.

AVAILABILITY

Can it participate now?

Tracks current availability of providers, components, or capabilities.

COORDINATION

Keep the system coherent

Coordinates ecosystem-level state and relationships without replacing specialized providers.

FAILURE HANDLING

Contain impact

Detect failure, assess impact, propagate state appropriately, and isolate unrelated functionality.

RECOVERY + DIAGNOSTICS

Return and understand

Coordinate restoration when possible and expose enough state to understand what happened and why.

Extension Model

Products expose surfaces. Add-ons plug into explicit contracts.

Extensions should be deliberate relationships, not accidental coupling. A product declares where it can be extended; an Add-on registers against that surface and follows its contract.

1 · Target

The product or component being extended.

2 · Extension Point

The named surface where extension is permitted.

3 · Contract

The rules the extension implementation must satisfy.

4 · Registration

The extension becomes known to the ecosystem and can be resolved for participation.

Bulk Product Edit
└── exposes → pricing.workflow

Bulk Price Manager
└── extends → pricing.workflow

Contract: receives pricing context → returns pricing result

Relationship Architecture

Relationships are fundamental — but not a separate eighth subsystem.

The Registry records relationships. The subsystem that owns the semantics of that relationship validates, resolves, or executes it.

Structural

Bundle contains Large Plugin. This expresses product composition, not runtime dependency.

Dependency

A component requires, optionally uses, recommends, or conflicts with another component.

Compatibility

A product or Add-on explicitly supports or rejects another product/version combination.

Capability

A component provides functionality or requires functionality from an eligible provider.

Extension

An Add-on or component extends an explicit surface exposed by another product.

Resolution principle

There is no universal relationship resolver; dependency, capability, compatibility, and extension systems resolve their own relationship types.
